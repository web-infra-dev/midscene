# Report e2e 覆盖范围

Report e2e 使用包含真实 Agent 录制数据的报告，验证核心用户流程。配置模型凭据后运行 `pnpm --filter @midscene/report e2e`，该命令会构建报告和 CLI、生成测试数据，通过 Midscene Test 跑完所有 YAML 测试后汇总失败。项目设置了 `test.bail: 0`，单个 Case 失败不会阻止后续文件执行。任何测试文件失败，命令仍会以失败状态退出。

## 开发原则

Report 的开发、评审和测试优先关注核心流程与数据正确性。日常迭代重点是用户能否读取结果、跳转 Case、查看失败信息和证据。间距、颜色、边框、阴影、圆角、图标外观和精确尺寸不作为默认验收条件，也不应引发反复验证；明确提出的设计要求再做针对性检查。

遮挡或截断重要信息、滚动异常、键盘操作失效等会阻断使用的问题属于功能缺陷。应围绕受影响的流程编写简短的结果断言。纯外观调整通常不需要自动化断言，也不要把脆弱的样式检查从 e2e 搬到单元测试中。

仓库级原则见开发文档的 [Report 开发与测试范围](../../../CONTRIBUTING.md#report-development-and-test-scope)。

## 结果口径

所有位置统一使用最终结果：Passed、Failed、Not run。Passed 包含此前失败、后来通过的 Case。通过条内部的描边留白部分、图例中的 “passed after retry” 数量及名称旁的警告图标表示历史，不是额外类别，也不会增加 Case 数。项目分组、筛选、数量和结果排序遵循同一口径。打开通过的 Case 默认展示最后一次执行，历史失败链接和 Attempts 仍可查看失败记录。整文件恢复通过的历史保留在 File 的 Attention 和 Project 提示中，一直通过的 Case 不继承该警告。File、Project 的作用域错误仍属于失败，不受 Case 通过率影响。

## 应覆盖的功能

- 加载 Agent、合并报告、旧版 YAML 和原生 Test 报告。
- 筛选、搜索、排序和展开 Project / File / Case 层级。
- 在 Case 之间跳转并保留概览状态，包括浏览器历史记录。
- 查看重试、初始化和清理失败、错误信息及 Case 累计 token 用量，包括模型用量提示。
- 查看录制、截图、JSON、任务信息和运行事件。
- 使用回放、模型详情、主题切换和移动端 Steps/Player 流程。

断言应简短，描述操作后可观察的结果。定位描述应包含区分相近控件所需的上下文，例如 Replay all tasks 与单任务 Replay 标签，以及 All cases 抽屉与执行步骤列表。排序应检查结果顺序，避免依赖箭头外观。数据正确性可以使用准确的测试数据值，与这些数据的视觉排列方式无关。

视图切换应检查内容，例如截图捕获信息或结构化 JSON，避免依赖标签的选中外观。对于响应式布局中只显示图标的操作，应实际操作并验证结果，不要求文字标签可见。

不要依赖源文件路径或文件名完整露出：CI 路径可能很长，页面会按设计截断。如果文件名不是被测行为，应通过所属 Project 和层级关系定位 File。操作可能被悬浮预览遮住的控件前，先将鼠标移到 Case 标题等不触发预览的位置。区分当前 Step 的 Record / Information / Events 标签和内嵌 Agent 录制中的控件；目标需要进一步检查时使用 `deepLocate`。

保留 `aiAssert`、`aiTap`、`aiHover` 等 AI 覆盖。JavaScript 用于需要确定性检查的浏览器集成，例如历史记录和 hash 变化、焦点、原生下拉框事件，以及导航前后的数值比较。避免检查 CSS 类名、颜色、边框、间距、尺寸和截图坐标。

聚合规则、序列化上限、状态转换和功能计算放在最近的单元测试中。涉及浏览器集成或用户流程时再增加 e2e。每个场景围绕一个流程，避免在不同测试文件中重复相同的导航和视觉检查。

生成的测试页面保存在被忽略的 `dist/` 中。测试运行期间应保持这些页面不变，并行构建会清空该目录。如必须并行构建，可把生成的静态页面复制到临时目录，并调整 `midscene.config.ts` 中静态服务器的路径，改为提供这份快照。
