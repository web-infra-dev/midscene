## AI 变革时代下的测试工程挑战

我们正处在一个 AI 变革的时代。在向自然语言测试迈进的过程中，测试工程面临着真实的转型痛点：

1. **对 Selector 模式的担忧**：传统的 Selector 模式不仅易碎、且非技术人员难以维护；更重要的是，它基于 DOM 树，无法真正模拟用户看到的真实界面（如元素遮挡、布局错乱），因而无法最大化发挥 AI 的视觉和语义理解价值。
2. **“为了 AI 而 AI” 的效能陷阱**：在转型大潮中，行业内常有“不用 AI 就很落后”的焦虑，导致团队盲目追求 100% 的 AI 覆盖率。将原本用确定性脚本（如 API 调用、数据准备）就能极速、稳定解决的后台任务，也硬性转用 AI 驱动。这不仅没有提升效率，反而导致效能下降、成本飙升——一旦陷入这种陷阱，反倒丢掉了我们对测试最朴素的追求：更快、更省钱、更稳定。
3. **工程与 AI 融合的组织体验挑战**：我们判断，未来的测试项目必然是“工程（代码）与 AI（自然语言）”的结合。然而，现有的测试框架在融合这两种形态时，往往在组织体验上不尽如人意。由于缺乏清晰的边界与协作模式，代码和自然语言容易混杂在一起，导致项目在长期维护中体验不佳。

大家渴望向自然语言转型，但缺少一条能连接“确定性代码”与“自然语言意图”的务实演进路径。

## 融合架构：声明式语义与确定性工程

为了打破上述困境，`@midscene/test` 回归端到端（E2E）测试的第一性原理，提倡**“声明式语义与确定性工程并重”的融合架构**。它将测试框架划分为两种相辅相成的对等能力，各司其职，完美契合了测试团队中的两种核心视角：

1. **确定性工程：TypeScript 编程构建坚实底座（TypeScript Node）**
   **聚焦“怎么保障” (How to support/setup)**。提供可编程的扩展能力，确保底层工程底座的确定性与高效率。
   该能力面向测试工程搭建者（平台或工具链研发人员）。他们负责使用 TypeScript 接入浏览器、Agent、外部工具和业务接口，统一管理运行资源和执行生命周期。工程搭建者只需在 TypeScript Node 中声明 Zod 规则与描述，通过自定义扩展节点对外提供高内聚、高确定的技术与业务能力，同时自动生成清晰的文档，无需耗费额外成本编写和维护 API 手册。

2. **声明式语义：自然语言表达业务期望（YAML + AI 动作）**
   **聚焦“测什么” (What to test)**。承载业务测试意图。通过声明式 YAML 组装用例。
   在该能力层，用例编写者可以直接用自然语言描述界面操作（如 `aiAct`）与校验（如 `aiAssert`），同时**无缝调用和装配由“确定性工程”所提供和暴露的各种专属业务节点（如 `order.prepare`）**。
   该能力面向业务场景。用例编写者可以直接用自然语言与声明式节点来装配复杂的业务用例，完全专注于业务测试流程，无需编写 JavaScript 或关注底层的代码实现与系统细节，显著提升了用例的编写效率与长期可维护性。

**定制专属测试框架与配套工程能力**

这一设计最核心的工程价值，在于赋予了开发者**定制专属测试框架**的能力。通过在“确定性工程”中注册符合自身业务背景的自定义 Node，您可以轻松拼装并扩展出一套高度贴合自身业务背景、高度内聚的定制化测试框架。

为了让开发者能够更加低成本、高效率地构建与运维这套专属框架，我们提供了一系列必不可少的配套工程能力支持：
* **统一的可观测性（Observability）**：无论是 AI 交互步骤还是您自定义 Node 的运行，都将被统一记录在执行生命周期中。测试报告与运行日志会完整呈现每一个步骤的入参、出参、耗时、执行状态与界面截图。这不仅极大地方便了人类工程师进行问题排查与回放，同时也为 AI Agent 自主化地诊断问题、优化用例提供了高度结构化的上下文数据。
* **标准的生命周期与并发控制**：为专属框架提供了完备的生命周期钩子（Before/After）、环境并发隔离与沙箱机制，确保定制用例在持续集成（CI）等环境中并发、稳定地运行。
* **自动生成 Node 说明书**：提供 `describe-nodes` 描述工具，能够将注册的自定义 Node 及其入参校验规则（Zod Schema）一键自动编译导出为标准的 Markdown 说明文档。这彻底免去了手动维护专属框架 API 手册的成本，方便用例编写者及 AI Agent 直接按需阅读与消费这些定制能力。

### 实战场景：验证订单退款流程

假设电商团队需要验证已支付订单的退款流程：

1. **确定性工程（TypeScript 节点）**：用例开始前通过自定义 Node `order.prepare` 提前准备测试订单，结束后执行 `order.cleanup` 清理。
2. **声明式语义（AI 自然语言）**：Agent 根据 YAML 中的自然语言指令，在页面上提交退款申请并检查结果。

#### 1. 自动导出的 Node 说明书示例

在此实战中，工程搭建者编写的 `order.prepare` 自定义节点，经过 `describe-nodes` 工具编译后，会自动生成如下 Markdown 说明书：

```markdown
## order.prepare

* **标题**：准备订单数据
* **说明**：在数据库中提前创建一个处于指定状态的订单。
* **参数格式 (JSON Schema)**：

{
  "type": "object",
  "properties": {
    "status": {
      "type": "string",
      "description": "订单状态，如 paid (已支付), refunded (已退款)。"
    }
  },
  "required": ["status"]
}
```

#### 2. 用例编写与运行（YAML）

用例编写者（或 AI Agent）阅读说明书后，可以直接在声明式 YAML 脚本中自由组装、调用该节点与 AI 动作：

```yaml
# 1. 确定性工程：数据与环境准备
beforeEach:
  - order.prepare:
      status: paid
  - browser.openRefundPage: {}

# 2. 声明式语义：表达业务测试意图
cases:
  - name: 已支付订单可以申请全额退款
    steps:
      - aiAct: 点击申请退款，选择全额退款并提交
      - aiAssert:
          prompt: 页面显示退款申请已提交，退款金额为订单的全部金额
          message: 全额退款申请提交失败

  - name: 已支付订单可以申请部分退款
    steps:
      - aiAct: 点击申请退款，输入退款金额 10 元并提交
      - aiAssert:
          prompt: 页面显示退款申请已提交，退款金额为 10 元
          message: 部分退款申请提交失败

# 3. 确定性工程：资源清理
afterEach:
  - order.cleanup: {}
```

框架维护者注册 `order.prepare`、`browser.openRefundPage` 和 `order.cleanup` 等自定义 Node 负责数据与页面管理，Midscene Node 负责界面操作与校验。测试意图与技术实现彼此分离，两类维护工作可以独立演进。
