# 创建和使用测试项目

本文从创建项目开始，介绍如何运行示例、了解可用的测试操作、编写 YAML 用例和查看运行结果。已有原生 Test 项目的读者可以直接从[了解可用的测试操作](#了解可用的测试操作)开始。

整体设计见 [Midscene Test 概览](./overview)。业务操作的实现方式见[编写自定义 Node](./extend)，运行环境和执行参数见[配置测试项目](./configuration)。

:::info 已有旧版 YAML 项目
这里的“旧版 YAML”特指由 `midscene` 执行的 `tasks/flow` 用例及 YAML 批配置，不包括原生 `cases/steps` Test 文件。旧链路只做兼容维护和必要修复，不再新增能力；现有项目可以继续运行，新项目和新增用例推荐使用 Midscene Test。两条链路共用执行内核和新的报告页面，具体命令边界与字段转换见[迁移到 Midscene Test](../migrate-to-midscene-test)。
:::

## 创建项目

### 1. 生成项目文件并安装依赖

准备 Node.js `^20.19.0 || ^22.12.0 || >=24.0.0` 和 pnpm。需要交互式引导时，运行：

```bash
pnpm dlx @midscene/test create
```

命令会依次提示选择项目目录、平台、包管理器，以及是否安装依赖。也可以直接传入参数，例如使用 pnpm 创建 Web 测试项目：

```bash
pnpm dlx @midscene/test create my-tests --platform web --package-manager pnpm
cd my-tests
```

可用参数如下：

| 参数 | 说明 |
| --- | --- |
| `[directory]` | 项目目录，可以是相对于当前目录的路径或绝对路径。使用 `.` 表示当前目录。省略时会提示输入，已有文件不会被覆盖。 |
| `--platform <value>` | 平台：`web`（Playwright）、`android`、`ios`、`harmony`（HarmonyOS）或 `computer`（桌面端）。省略时会提示选择。 |
| `--package-manager <value>` | 包管理器：`npm` 或 `pnpm`。省略时，交互式终端会提示选择；非交互式环境会检测调用命令的包管理器，无法识别时使用 `npm`。 |
| `--yes`、`-y` | 跳过交互并安装依赖。必须同时提供目录和 `--platform`；与 `--skip-install` 同用时只生成文件。 |
| `--skip-install` | 只生成文件，不安装依赖，也不生成 Node 说明书。之后执行安装命令即可生成说明书。 |
| `--help`、`-h` | 查看命令帮助和示例。 |

每个平台目前提供一个起步模板，通过 `--platform` 选择，均使用原生 `cases/steps` Test 文件。在 CI 等非交互式环境中，必须提供目录和 `--platform`；未设置 `--skip-install` 时会安装依赖。

常用示例：

```bash
# 创建 iOS 项目并安装依赖，全程不询问
pnpm dlx @midscene/test create my-ios-tests --platform ios --package-manager pnpm --yes

# 只生成 Web 项目文件
pnpm dlx @midscene/test create my-web-tests --platform web --package-manager pnpm --skip-install

# 查看完整参数
pnpm dlx @midscene/test create --help
```

按提示安装依赖。命令会生成平台配置和示例用例，安装依赖后还会生成 Node 说明书。Web 项目的主要文件如下：

```text
my-tests/
├── cases/todo.yaml             # TodoMVC 用例
├── nodes/todo.ts               # Web 自定义 Node：初始化、校验和状态记录
├── midscene.config.ts          # 平台配置与 Node 注册
├── midscene-node-spec.web.md    # 安装后自动生成的 Node 说明书
├── package.json
├── tsconfig.json
├── .env.example
├── README.md
└── README.zh.md
```

其他平台模板在 `midscene.config.ts` 中定义 `todo.setup`，不包含 `nodes/todo.ts`，说明书文件名使用对应平台名称，例如 `midscene-node-spec.ios.md`。创建项目和生成说明书不会运行测试，因此这一步不需要模型 API Key、浏览器或设备。生成项目中的 README 会说明平台准备和示例运行方式。

:::info 安装恢复
如果跳过安装或安装失败，可以进入项目目录执行 `pnpm install`。需要重新生成 Node 说明书时，执行 `pnpm run nodes`。
:::

### 2. 配置模型与运行环境

将 `.env.example` 复制为 `.env`，按照[模型配置](../model-config)填写模型名称、服务地址和 API Key。

运行测试前，检查模型连接和 Midscene 兼容性：

```bash
pnpm exec midscene-test model verify
pnpm exec midscene-test model verify --help
```

命令会读取当前工作目录下的 `.env`，并覆盖已有的 Shell 环境变量，无需浏览器或设备。详见[模型调试与可观测性](../model-debugging-observability)。

Web 项目还需要安装 Chromium：

```bash
pnpm exec playwright install chromium
```

其他平台在创建时修改 `--platform`，并完成对应准备：

| 平台 | 参数值 | 运行前准备 | 环境配置指南 |
| --- | --- | --- | --- |
| Android | `android` | 连接设备，可用 `ANDROID_DEVICE_ID` 选择设备。 | [配置指南](../platforms/android) |
| iOS | `ios` | 启动 WebDriverAgent。直连时配置 `WDA_HOST` 和 `WDA_PORT`，通过网关时配置 `WDA_BASE_URL`；远程视频流使用 `WDA_MJPEG_URL`，直连则可使用 `WDA_MJPEG_PORT`。 | [配置指南](../platforms/ios) |
| HarmonyOS | `harmony` | 用 `hdc list targets` 检查连接，可用 `HARMONY_DEVICE_ID` 选择设备；PATH 中没有 HDC 时设置 `HDC_HOME`。 | [配置指南](../platforms/harmonyos) |
| 桌面端 | `computer` | 安装依赖并授予权限，可用 `COMPUTER_DISPLAY_ID` 选择显示器。无界面 Linux 还需安装 Xvfb 并启用 `MIDSCENE_COMPUTER_HEADLESS_LINUX`。 | [配置指南](../platforms/desktop) |

### 3. 运行生成的示例

```bash
pnpm test
```

五个平台的模板都使用在线 React TodoMVC，演示添加、删除和完成任务。运行测试的浏览器或设备需要能访问该网站。

Web 模板在每条用例前通过 `todo.setup` 打开 All 视图、清空页面存储并重新加载，使用 DOM 确认列表为空，再由 `todo.seed` 添加三个任务，第一条用例校验初始状态，第二条用 AI 删除和完成任务后校验结果；每条用例后由 `todo.captureState` 记录页面状态。Android、iOS、HarmonyOS 和桌面端模板使用 AI 添加三个任务、删除一个、完成另一个、切换到已完成筛选，并校验结果。修改任务前，这些模板先通过 `todo.setup` 打开 All 视图并等待输入框，再由 `aiAssert` 检查列表为空（包含已完成任务）且没有遮挡弹窗。已有任务会保留；检查失败时，请切换到 All 删除全部任务，或仅清除 TodoMVC 网站的数据，关闭遮挡弹窗后重新运行。模型或连接异常应先按报告中的原因排查。AI 检查可能误判，失败时请结合报告确认页面状态。所有模板均串行运行，首次用例失败即停止后续用例（`test.bail: 1`），同时正常保存报告、释放资源。

运行结束后，可以在 `midscene_run/report/` 查看报告，了解各用例及步骤的执行结果。随后修改 `cases/todo.yaml` 编写自己的用例，可用操作及其参数以生成的 Node 说明书为准。

## 了解可用的测试操作

### 官方操作与按需扩展

Midscene Test 将每一种可在 YAML 中调用的能力称为 **Node（节点）**。

Node 既可以在用例的 `steps` 中调用，也可以在 `beforeEach`、`afterEach` 等[生命周期钩子](#定义执行生命周期)中调用，写法相同。

所有平台都提供以下常用能力：`aiAct` 根据自然语言操作界面，`aiAssert` 检查预期结果，`aiWaitFor` 等待可观察条件成立，`wait` 等待指定时长。

在这些通用能力之外，Midscene 还为各个平台预置了专用操作。例如：

- **Web**：`gotoUrl` 打开网页、`setCookies` 设置 Cookie、`setViewportSize` 调整浏览器视口大小。
- **Android**：`launch` 启动应用、`back` 返回上一页、`home` 返回主屏幕、`runAdbShell` 执行 ADB 命令。

创建项目时，脚手架会根据选择的平台显式注册相应的官方 Node。手写 `midscene.config.ts` 时不会隐式注册任何 Node，需要自行配置。开发者也可以按需扩展，例如通过业务接口准备测试订单，详见[注册自定义业务 Node](./extend#注册自定义业务-node)。

### 生成当前项目的 Node 说明书

不同平台、执行项目和项目版本实际注册的 Node 可能不同。不要根据其他项目的示例推测当前项目的可用能力；`midscene-test nodes` 根据最终生效的注册结果生成 Node 说明书，它是当前项目可用 Node 名称、输入字段和字符串简写方式的事实来源。人类和 AI Agent 都应根据这份 Node 说明书编写 YAML 用例。

脚手架会在安装依赖后自动生成。修改 `agentClass`、顶层 `nodes`、`projects[].nodes`、Node schema，或者升级相关 Midscene 包后，应重新生成：

```bash
pnpm run nodes
```

也可以直接运行命令，并指定测试目录、配置文件或执行项目：

```bash
pnpm exec midscene-test nodes ./e2e --config ./config/midscene.config.ts
pnpm exec midscene-test nodes --project android-smoke
```

配置了 `projects` 时，`midscene-test nodes` 默认按执行项目分别生成说明书，即使各项目的 Node 定义完全相同。文件名为 `midscene-node-spec.<project-name>.md`。使用 `--project <name>` 只生成指定项目的说明书，文件名保持一致。未显式配置 `projects` 时，文件名仍为 `midscene-node-spec.md`。文件写入指定目录；省略目录时写入当前目录。在 `package.json` 所在目录运行命令即可将说明书保存在该目录。Project name 重复，或转换后的文件名冲突（包括大小写差异），都会在写入任何文件之前抛错。

生成命令只加载项目配置和 Node 定义，不执行 setup、用例或 `getAgent`，因此不需要启动浏览器、连接设备或调用模型。说明书是生成文件，不要手动编辑；配置变化后重新执行命令。

说明书包含两个部分：Available Nodes 列出可用 Node，Node Details 展示每个 Node 的 description、字符串简写规则和输入结构。输入结构由 Zod `inputSchema` 转换为标准 JSON Schema。说明书和终端输出均优先列出 `aiAct`、`aiAssert`，其余 Node 按名称排序。

说明书还会列出用例文件的匹配规则（`Case files`）和配置文件路径（`Config file`），方便用例编写者定位文件。`Case files` 对应各执行项目的 `files.include` 和 `files.exclude`。这两类路径均相对于说明书所在目录。

## 编写 YAML 测试用例

### 一个典型的 YAML 文件

一个 YAML 文件可以包含多个测试用例，以及用例执行前后的准备和清理步骤。下面以商城搜索为例：每次运行用例前打开首页，再搜索商品并检查结果。请将网址和商品名称替换为你的业务内容。

```yaml filename=cases/search.yaml
beforeEach:
  - gotoUrl: https://your-shop.example

cases:
  - name: 搜索商品
    steps:
      - aiAct: 在搜索框输入“马克杯”，点击搜索按钮
      - aiAssert: 搜索结果中包含马克杯
```

文件中各部分的含义如下：

- `beforeEach`：每个用例执行前运行的步骤。它是可选的，适合打开页面、重置状态等准备操作。其他钩子见[执行生命周期](#定义执行生命周期)。
- `cases`：测试用例列表，至少包含一个用例。需要增加用例时，在列表中添加新的 `name` 和 `steps`。
- `name`：用例名称，用于在运行结果中识别这个用例。
- `steps`：按顺序执行的步骤，至少包含一个步骤。每个步骤只能调用一个 Node，冒号后填写调用参数。

文档中把整个 YAML 文件称为 Workflow Document（工作流文档），把一个用例称为 Case，把一次 Node 调用称为 Step（步骤）。

示例使用字符串简写：`gotoUrl` 后的文本作为 `url`，`aiAct` 和 `aiAssert` 后的文本作为 `prompt`。需要传入更多参数时，可以使用下文的对象写法。是否支持简写，以项目的 Node 说明书为准。

### 关键 Node：操作与断言

日常用例主要通过 `aiAct` 描述操作，通过 `aiAssert` 检查结果：

| Node | 用途 | 编写方式 |
| --- | --- | --- |
| `aiAct` | 根据自然语言完成界面操作，可以包含多个动作。 | 描述要做什么，例如“搜索马克杯，将第一个商品加入购物车”。 |
| `aiAssert` | 检查界面是否满足预期；不满足时，步骤失败。 | 描述可观察的结果，例如“购物车中有一件马克杯”。 |
| `aiTap` | 点击一个指定目标。 | 描述要点击的元素，例如“页面右上角的购物车图标”。 |

操作完成不代表测试通过，应使用 `aiAssert` 明确检查预期结果。需要自定义断言失败信息时，可以展开参数：

```yaml
steps:
  - aiAct: 搜索马克杯，将第一个商品加入购物车
  - aiTap: 页面右上角的购物车图标
  - aiAssert:
      prompt: 购物车中有一件马克杯
      message: 加购后购物车内容不符合预期
```

`aiAct` 支持可选的 `options.effort`，用于选择规划投入程度：`fast`、`balance` 或 `deepThink`。省略时沿用 Agent 默认行为；同时提供 `deepThink` 时，`effort` 优先。例如：

```yaml
steps:
  - aiAct:
      prompt: 完成结算
      options:
        effort: deepThink
```

### 设置 AI 上下文

推荐在 `beforeAll` 中调用 `setAIContext`，这样可以在当前文档的用例执行前统一配置上下文，让配置对后续使用同一个 Agent 的所有相关 AI 操作生效。也可以在 `beforeEach` 或用例的 `steps` 中调用，按需设置或清除上下文；修改从调用时开始生效。

参数与 `agent.setAIContext(target, context)` 一致：`target` 可以是 `default` 或 `aiAct`、`aiTap`、`aiAssert` 等 AI API 名称。

**设置 context**：传入 `context` 字符串，设置对应 API 的上下文；使用 `target: default` 可以设置各 AI API 共用的默认上下文。

```yaml
beforeAll:
  - setAIContext:
      target: aiAct
      context: |
        整个流程使用测试账号。
        如出现优惠券弹窗，关闭后继续。
```

**清除 context**：省略 `context`，等同于传入 `undefined`，移除 `target` 对应的配置。

```yaml
beforeAll:
  - setAIContext:
      target: aiAct
```

清除某个 API 的上下文后，该 API 会回退到 `default`；清除 `default` 则移除共用的默认上下文。如果需要禁用某个 API 继承的上下文，可以将其 `context` 设为空字符串 `""`。

单次调用的 `options.context` 优先于 Agent 级配置，各层上下文不会拼接。配置属于 Agent 实例：`beforeAll` 与用例需要使用同一个 Agent；修改会持续生效，直到被覆盖或清除。

### 其他 Node 的调用模式

平台操作和自定义业务 Node 使用相同的调用结构：**Node 名称下面填写参数**。下面展示多参数和无参数两种常见形式，这些片段可以放入用例的 `steps` 中：

```yaml
steps:
  - setViewportSize:
      width: 1440
      height: 900
  - clearCookies: {}
```

`setViewportSize` 接收一个参数对象；`clearCookies` 无需参数，使用 `{}`。这两个 Node 由 Web 项目提供。移动端、桌面端以及团队自定义 Node 的可用范围和参数，以当前项目的说明书为准。

例如，如果团队注册了创建订单的 `order.create`，就可以这样调用。该 Node 是业务扩展示例，使用前需要在项目中实现和注册：

```yaml
steps:
  - order.create:
      sku: midscene-mug
      quantity: 2
```

参数还可以包含嵌套对象或数组。比如给 `aiAct` 传入参考图时，文字和图片共同组成 `prompt`；`options` 则单独填写：

```yaml
steps:
  - aiAct:
      prompt:
        prompt: 按照参考图完成设置
        images:
          - name: 目标状态
            url: ./fixtures/target.png
      options:
        deepLocate: true
```

### 设置超时和错误处理

`$` 用于设置由 Midscene Test 控制的 Step 参数。Midscene Test 不会将这些参数传入 Node 的 `input`。

```yaml
steps:
  - order.create:
      sku: midscene-mug
      quantity: 1
      $:
        timeout: 30000
        continue-on-error: true
```

支持以下两个字段：

- `timeout`：Step 的超时时间，单位为毫秒。
- `continue-on-error`：设为 `true` 后，Step 失败时允许继续执行当前阶段的后续 Step。默认值为 `false`。操作未退出或资源清理异常时，仍会停止执行。

`continue-on-error` 只控制 Midscene Test 是否继续执行。只要有 Step 失败，Case 的最终状态就是 `failed`。

超时不代表底层操作已经退出。继续同阶段的后续 Step 前，框架会等待已取消的操作结束，默认最多 30 秒；仍未结束就停止后续步骤。等待单独计时，不占下一步的超时预算。操作结束后可以继续使用 Agent，但页面和业务状态仍需由用例确认或重置，见[超时与取消机制](./configuration#超时与取消机制)。

### 使用项目变量与环境变量

Midscene Test 会在执行前递归解析 Node input：

```yaml
steps:
  - launch:
      uri: ${appUri}
  - api.createOrder:
      baseURL: ${{TEST_API_BASE_URL}}
      payload:
        count: ${orderCount}
```

- `${name}` 读取当前执行项目的 `variables`；独占整个标量时保留原始 JSON 类型。
- `${{ENV_NAME}}` 读取环境变量，结果始终是字符串。
- 对象或数组变量可以作为完整值使用，但不能嵌入更长的字符串。
- 未定义变量会在收集阶段失败。变量只解析 Node input，不解析 `$`。

Workflow YAML 不提供 `set`、`saveAs` 或 Step 输出表达式。每个 Step 独立运行，不会自动接收前序 Step 的结果。如需共享必要信息，请通过执行项目的 `context` 显式提供。

### 使用 tags 筛选 Case

```yaml
cases:
  - name: Android 冒烟下单
    tags: [smoke, android]
    steps:
      - aiAct: 完成下单
```

框架维护者在每个执行项目中配置 `tags.include` 与 `tags.exclude`。exclude 始终优先；include 非空时，Case 命中任意一个 include tag 即会被选中。

## 定义执行生命周期

本节介绍单个 YAML 文件的生命周期。项目 `setup`、文件钩子、用例和清理之间的完整关系，见[项目、文件与用例的生命周期](./configuration#项目文件与用例的生命周期)。

### 准备与清理步骤

生命周期钩子用于在用例执行前后准备环境、重置状态或清理数据。四个钩子都是可选的，与 `cases` 同级；其中的步骤和用例 `steps` 使用相同的 Node 调用写法。

| 钩子 | 执行时机 | 常见用途 |
| --- | --- | --- |
| `beforeAll` | 当前 YAML 文件的所有用例开始前，执行一次 | 准备本文件共用的测试数据 |
| `beforeEach` | 每个用例的每次执行开始前，包括重试 | 打开页面、重置用例状态 |
| `afterEach` | 每个用例的每次执行结束后，包括失败和重试 | 清理本次用例创建的数据 |
| `afterAll` | 当前 YAML 文件的所有用例结束后，执行一次 | 清理本文件共用的测试数据 |

下面的 Web 示例在每个用例开始前打开商城首页，结束后清除 Cookie。`data.prepare` 和 `data.cleanup` 是需要由项目实现和注册的自定义 Node，分别准备和清理测试商品；`gotoUrl`、`clearCookies`、`aiAct` 和 `aiAssert` 是 Web 脚手架默认注册的官方 Node。请替换示例网址和商品名称。

```yaml filename=cases/search.yaml
beforeAll:
  - data.prepare: 准备马克杯和水壶两种测试商品

beforeEach:
  - gotoUrl: https://your-shop.example

cases:
  - name: 搜索马克杯
    steps:
      - aiAct: 搜索马克杯
      - aiAssert: 搜索结果中包含马克杯

  - name: 搜索水壶
    steps:
      - aiAct: 搜索水壶
      - aiAssert: 搜索结果中包含水壶

afterEach:
  - clearCookies: {}

afterAll:
  - data.cleanup: 删除本文件准备的测试商品
```

### 执行顺序与重试

没有失败或重试时，上面文件的执行顺序为：

```text
beforeAll
  用例 1：beforeEach → steps → afterEach
  用例 2：beforeEach → steps → afterEach
afterAll
```

配置重试后，失败的用例会在本次清理完成、没有操作仍在运行时，在重试次数范围内重新执行 `beforeEach → steps → afterEach`，再继续后续用例。重试不会重新执行 `beforeAll`，`afterAll` 仍在文件结束时运行一次。重试次数是上限：操作未退出、清理等待或清理失败都会提前停止重试。

### 失败时如何执行

- `beforeEach` 失败：跳过当前用例的 `steps`，仍执行 `afterEach`。
- 用例的 `steps` 失败：仍执行 `afterEach`。
- `beforeAll` 失败：当前文件的用例标记为 `not-run`，仍执行 `afterAll`。
- `afterEach` 或 `afterAll` 失败：记录为失败，不会因为它是清理步骤而忽略错误。

默认情况下，一个阶段中的步骤失败后，该阶段的剩余步骤不再执行。需要继续执行同阶段的后续步骤时，可设置 [`continue-on-error`](#设置超时和错误处理)；这不会把失败结果改为成功。清理 Node 应能处理准备步骤只完成了一部分的情况。

默认情况下，一个 Case 失败后仍会继续执行下一个 Case。需要提前停止调度时，通过 `test.bail` 设置失败用例数阈值。文件级前置条件放在 `beforeAll`，失败后该文件的 Case 不再执行；有依赖关系的业务步骤放在同一个 Case 中，不要依赖另一条 Case 成功。

资源异常是上述继续规则的例外：操作未退出或注册的清理函数等待、失败时，不再重试，也不执行同文件后续 Case。CLI 还会停止调度该项目的后续文件，因为它们共享 `context`；独立项目可以继续执行。普通 `afterEach` Step 失败仍按用例失败处理，只要操作已退出且注册的清理完成，就可以重试。报告写入等运行基础设施错误会取消整次运行。

项目 setup 管理浏览器和 Agent 等资源，详见[使用 setup 创建和清理共享资源](./configuration#使用-setup-创建和清理共享资源)。Node 内部创建的资源，见[资源的生命周期与清理](./extend#资源的生命周期与清理)。

## 运行测试

在项目根目录下，使用以下命令运行 YAML 测试用例：

```bash
pnpm exec midscene-test
```

### 指定用例目录或文件

生成的项目通过 `files.include` 选择 `cases/` 下的 `.yaml` 和 `.yml` 文件。未配置 `files` 时，Midscene Test 会递归查找测试目录下的 YAML 文件，自动忽略 `node_modules` 和 `.git`。

如果你只想执行特定目录或特定用例文件，可以将其作为参数传入：

```bash
# 运行指定目录下的所有用例
pnpm exec midscene-test ./cases/smoke

# 运行单个指定的用例文件
pnpm exec midscene-test ./cases/order.yaml
```

### 过滤运行目标与配置文件

如果项目配置了多个运行平台或环境，你可以指定仅运行特定的执行项目，或者通过命令行指定自定义配置文件：

```bash
# 只运行名为 android-smoke 和 ios-regression 的执行项目
pnpm exec midscene-test --project android-smoke --project ios-regression

# 使用指定的配置文件运行测试
pnpm exec midscene-test --config ./config/midscene.config.ts
```

为某个执行项目生成 Node 说明书时，也可以指定 `--project`：

```bash
pnpm exec midscene-test nodes --project android-smoke
```

### 尚未迁移的旧版 YAML 继续使用旧命令

顶层使用 `tasks/flow` 的旧文件和 YAML 批配置继续使用 `midscene`：

```bash
pnpm exec midscene ./legacy-flow.yaml
pnpm exec midscene --config ./legacy-batch.yaml
```

`midscene-test` 不会自动识别或执行这些旧文件，也不接受旧批配置和旧 CLI 参数。一个文件完整转换为 `cases/steps` 后，才能改用 `midscene-test`。迁移期间，两类文件可以放在同一仓库的不同目录，但同一次命令只能选择一种格式。迁移步骤和字段映射见[迁移到 Midscene Test](../migrate-to-midscene-test)。

需要把结构化运行结果写到指定目录时，使用 `--result-dir`：

```bash
pnpm exec midscene-test --result-dir ./test-results
```

当发生用例运行失败、文档解析失败或收集阶段发生错误时，CLI 会返回退出码 `1`。

## 查看测试结果

每次运行结束后，CLI 会打印执行结果和 `Report:` 路径。打开 HTML 报告，即可查看项目、Case、重试记录、截图、Step 输入输出、错误及关联的 Agent 执行详情。

**Test Report** 总览展示 **Project → File → Case** 三层结构，左侧导航按 Failed、Passed after retry、Passed、Not run 的顺序分组展示项目，选择 Project 后在右侧查看其 File/Case 表格。每个分组名称后显示匹配的项目数，Projects 标题不重复展示总数。展开 File 可以查看其 Case；有失败、文件级错误或重试后通过 Case 的 File 默认展开。空文件和收集失败的文件仍然可见，错误显示在所属 File 下方。Project 初始化、清理错误显示在项目标题下。**Compact** 展示 Case 名称、结果、重试信息和耗时；进入失败 Case 查看错误详情。**Detailed** 在相同 Case 集合下增加截图时间线和简短的报错或未执行原因；重试后恢复的错误会标明来自此前尝试。点击摘要可查看错误详情，点击截图可进入对应 Step。

搜索框查找整个报告中的 Project、File、Case 和错误详情，左侧导航只保留有匹配内容的 Project。选中项目标题旁的 **All / Failed / Passed / Retried** 复选框只筛选该 Project。没有匹配内容时，空态中的 **Clear filters** 可清空搜索并恢复 All：

- **All** 包含 Not run Case 和没有 Case 的文件。选择具体状态会取消 All；多个具体状态按 OR 匹配，取消最后一个具体状态会恢复 All。
- **Failed** 包含失败 Case 和文件、项目级错误。受影响的 Not run Case 作为上下文保留，但不计入失败数。
- **Retried** 表示 Case 在此前的 Case 尝试失败后最终通过。文件整体重试不代表其中所有 Case 都属于 Retried。筛选中的 **Passed** 仅包含此前没有失败 Case 尝试的通过用例，顶部 Passed 汇总包含这两类。
- 复选框的悬浮提示和无障碍标签以 Case 为单位显示计数，范围是选中 Project 的搜索结果；文件和项目级错误不计作 Case 失败。筛选不会改变顶部运行汇总或 File 的完整执行 **Passed / Case** 计数。File 只显示通过数 / 总数，不额外显示百分比和逐文件匹配提示；Case 总数未知或为零时显示 **—**。

点击 Project 表格的 **Files**、**Passed / Case**、**Attention** 或 **Duration** 列头，可单独排序该 Project；**Passed / Case** 按通过率排序。Project 按最终结果分组，同组内保持报告顺序；File 只在所属 Project 内排序，Case 只在所属 File 内排序。**Files** 默认采用报告中的文档顺序，与 Markdown 结果一致；再次点击则反向排列。仅存在于计划中的文件和收集错误接在已报告文档之后，保持各自原有顺序。按 **Files** 排序时，文件内 Case 保持 `caseIndex` 顺序。其他列可切换方向，未知值始终置后。File Duration 使用记录的文件耗时，Case Duration 汇总其全部尝试的记录耗时。切换 Project 会恢复 **All**，并保留搜索和各 Project 的排序；**Clear filters** 也保留排序。进入 Case 再返回 Overview 时，选中的 Project、搜索、状态筛选、各 Project 的排序、File 展开状态和导航分组的折叠状态均保留。只有一个 Case 的报告仍在首次打开时直接进入详情，其 Overview 链接可以返回层级总览。

旧 **tasks / flow** YAML 新生成的报告使用同一页面：每个 task 对应一个 Case，flow 条目对应 Step。内联输入显示为 **Inline YAML**。宿主初始化、清理错误归属于 File，不虚构 YAML 中的钩子。旧 CLI 批量执行和整文件重试报告仍保留来源身份，此页面不会把独立报告推断合并成同一个逻辑 Project，也不会推断 Case 重试历史。只有 Agent dump 的来源标注为 **Source report / Agent report**，不声称还原出 YAML 文件或 task、flow 导航。仅在存在真实原文快照时提供 YAML 视图。历史 HTML 报告需重新生成才能使用新布局。

Case 的 **Execution** 表头集中展示 **Visual / YAML** 切换、多次尝试时的 **Attempts** 下拉框，以及 Step 状态统计。报告保存了源 YAML 快照时，才可使用 YAML 视图。Visual 视图在截图时间线下方展示统一的 Step 列表和选中 Step 的详情，列表中的生命周期分组使用分割线区分。在宽屏下，拖动分栏线可调整 Step 列表宽度，聚焦后也可使用方向键调整，双击可恢复默认宽度。打开包含失败 Step 的 Case 时，会选中该 Step，并将对应行和错误滚动到可见位置。

选中 Step 后，可以查看 **Information** 和 **Events**；有录屏或截图证据时，还会显示 **Record**：

- **Record** 展示关联的 Agent 执行过程或截图。悬停时间线缩略图可以预览，点击后会选中截图所属的 Step。
- **Information** 按对齐的行展示 Input、Output 和 Stable IDs。有对应数据时，还会展示配置、Planned input 和 **Information captured at**（信息采集时间）。采集时间按浏览器本地时区显示，包含毫秒和 UTC 偏移，不一定是 Step 的结束时间。悬停可查看原始 UTC 时间，以及前往 **Events** 查看后续完成或取消情况的说明。
- **Events** 以表格展示 Time、Operation、Event 和 Status。缺少详细操作事件时，会根据已知时间展示 Step 的开始和结束；没有事件的 Step 会显示空状态。

**Operation** 列说明正在执行什么。悬停 Operation 或 Event 文案，可以查看原始日志名称及解释；Operation 提示还保留了 Operation ID，方便对照日志。

| Operation 文案 | 原始名称 | 含义 |
| --- | --- | --- |
| Run step | `node` | 执行整个 Step，包含其内部的 Agent 操作；内置和自定义 Node 都有这一层。 |
| Get Agent | `acquisition` | 获取本次 Step 使用的 Agent，可能复用已有实例。 |
| Run Agent operation | `resource` | 通过 Agent 执行操作，例如点击、断言或记录截图。 |
| Wait for app readiness | `readiness` | 动作完成后，等待配置的就绪回调。 |
| Clean up resources | `cleanup` | 清理执行过程中使用的资源。 |

这些操作不是互不重叠、依次执行的阶段。**Run step** 包含其内部操作，因此不能把内部操作耗时再加到 Step 总耗时上。例如，Runner 的 `wait` 和不经过 Agent 适配层的自定义 Node 只有 **Run step** 事件；`aiAct`、`aiAssert` 通常在 **Run step** 内先获取 Agent，再执行 Agent 操作。规划、定位及具体页面动作请查看 **Record**。

| Event 文案 | 原始名称 | 含义 |
| --- | --- | --- |
| Started | `started` | 操作开始。 |
| Finished | `settled` | 操作已结束，成功或失败看 Status。 |
| Result returned | `runner-returned` | Runner 已返回 Step 结果，底层操作可能仍未结束。 |
| Cancellation requested | `cancel-requested` | 已请求取消，但操作可能仍在运行。 |
| Cleanup postponed | `cleanup-deferred` | 尚未结束的操作仍在使用资源，清理被推迟。 |

**Execution still running** 和 **pending** 徽标表示 Runner 返回结果时，操作尚未结束，可能出现在超时或取消场景。这不代表报告记录截止时间之后的实时状态。Status 为 `-` 表示这条事件没有结果状态，不代表失败。

Step 错误显示在这些标签页上方。展开 **details** 可查看技术信息；存在多个问题时，可通过 **View all … issues** 查看。Case 和生命周期清理错误仍显示在 Execution 上方。页头的主题按钮可以切换浅色和深色主题。

报告保留执行前的测试计划，以及实际执行和未执行的步骤、未执行原因、重试停止原因。等待旧操作退出的时间与步骤执行时间分开记录。报告是生成时的快照：`cleanup pending` 表示当时清理尚未完成，资源仍保持隔离；之后完成的清理不会回写已生成的 HTML。

报告默认保存在：

```text
midscene_run/report/midscene-e2e-<runId>.html
```

使用外置截图时，报告是包含 `index.html` 和 `screenshots/` 的目录，复制或上传时需保留整个目录。

通过 `midscene.config.ts` 中的 `output.reportDir` 可以修改报告目录。

### 链接到报告中的 Step

使用 URL Hash 参数 `runner-step`，可以直接打开报告中的指定 Step。除了具体的 Step ID，报告还支持不依赖运行 ID 的通用选择器：

| 选择器 | 定位目标 |
| --- | --- |
| `first` | 最早开始执行的 Step |
| `last` | 最晚执行完成的 Step |
| `first-error` | 最早开始执行的失败 Step，包括失败的重试记录 |
| `last-error` | 最晚执行完成的失败 Step，包括失败的重试记录 |

URL 没有指定 Case 路由时，选择器会搜索整份报告。URL 同时包含 `runner-page=case`、`runner-project` 和 `runner-case` 时，选择器只搜索这个 Case。没有匹配的 Step 时，报告会显示提示，并且不会打开无关的 Agent 执行详情。

例如，以下 URL 会打开报告中最后一个失败的 Step：

```text
https://example.com/report/index.html#runner-step=last-error
```

如果该 Step 关联了 Agent 执行详情，可以增加 `runner-trace=page`，直接以整页方式打开 Agent 执行详情：

```text
https://example.com/report/index.html#runner-step=last-error&runner-trace=page
```

## 用例设计约定

Midscene Test 通过顺序执行和显式共享状态，让每个 Node 的输入、执行上下文和依赖关系更清晰。YAML 用例遵循以下设计：

* **按声明顺序执行**：YAML 描述线性的测试步骤，不引入 DAG、分支或循环语法。对于需要复杂编排的场景，建议在更上层构建 YAML 脚本生成能力，将编排结果生成为明确的步骤序列，再交给 Midscene Test 执行。
* **每个节点是无状态的**：每次 Node 调用依赖当前声明的输入和项目显式提供的上下文，不会自动继承前序 Step 的输出。YAML 不提供跨步骤或跨用例的输出引用语法；需要共享业务状态时，应在自定义 Node 中读取和更新项目 `context`，并实现相应的业务逻辑。

例如，下面的断言使用“上一步的图标”指代目标，依赖前一步的指令上下文，是错误的写法：

```yaml
steps:
  - aiAct: 点击商品详情页的收藏星标，将其点亮
  # 错误：断言不会继承前一步的指令上下文，无法通过“上一步的图标”明确识别目标。
  - aiAssert: 上一步的图标已经点亮
```

应在断言中明确写出检查对象和预期状态，让这条断言本身就能表达完整的检查条件：

```yaml
steps:
  - aiAct: 点击商品详情页的收藏星标，将其点亮
  - aiAssert: 商品详情页的收藏星标处于点亮状态
```

界面状态会保留前一步操作的结果，但后续 Node 的指令应独立描述目标，不依赖“上一步”“刚才那个”等指代。
