# Run tests

## Basic usage {#run-tests}

Run YAML test cases from the project root:

```bash
pnpm exec midscene-test
```

### Specify a test case directory or file

Projects generated from templates use `files.include` to match `.yaml` and `.yml` files under `cases/` by default. If `files` is not declared in the configuration, Midscene Test recursively searches for all YAML files under the test root directory (automatically ignoring `node_modules` and `.git`).

File and directory arguments only narrow the selected cases; they do not change the project context.

- **Config discovery**: Look for `midscene.config.ts` or `midscene.config.mjs` in the current working directory only. No parent or child directories are searched. Resolve an explicit `--config` path relative to the working directory.
- **Test root**: Use the config's directory, or the working directory when no config is found. Resolve `files.include`, `files.exclude`, and `output.reportDir` relative to this root.
- **CLI paths**: Resolve the file/directory argument and `--result-dir` relative to the working directory.
- **Selection**: Apply `--project`, configured file inclusion/exclusion, and tags. The positional path further narrows this selection; it never bypasses exclusions. If no cases match, the command fails with a selection error.

From the project root, these commands share the same config, Nodes, and default output directory:

```bash
pnpm exec midscene-test
pnpm exec midscene-test ./cases/order.yaml
pnpm exec midscene-test ./cases/smoke
pnpm exec midscene-test ./cases/order.yaml --config ./midscene.config.ts
```

From a child directory, select the project config explicitly:

```bash
cd cases
pnpm exec midscene-test ./order.yaml --config ../midscene.config.ts
```

A directory argument no longer switches projects. To run another project, change into its directory or use `--config` to select its config. In the SDK, use `projectRoot` to choose the config discovery directory and `testPath` to filter files; an explicit `configPath` is relative to `cwd` and its directory becomes the root.

### Filter execution targets and configuration files

If a project defines multiple platforms or environments, you can use `--project` to run specific Execution Projects, or use `--config` to specify a custom configuration file:

```bash
# Run only the android-smoke and ios-regression Execution Projects
pnpm exec midscene-test --project android-smoke --project ios-regression

# Run tests with a specific configuration file
pnpm exec midscene-test --config ./config/midscene.config.ts
```

When generating the Node Spec for a specific Execution Project, you can also use `--project`:

```bash
pnpm exec midscene-test nodes --project android-smoke
```

## Output and exit codes

### Terminal output mode

By default, the terminal prints summarized execution results grouped by Case. To view detailed step diagnostics, use the `verbose` reporter. Run `--help` to view all supported CLI options:

```bash
# Show detailed step diagnostics
pnpm exec midscene-test --reporter verbose

# View all CLI options
pnpm exec midscene-test --help
```

### Result files and report paths

Each run generates two types of output artifacts. Their exact paths are printed at the end of the terminal output as `Summary:` and `Report:`:

- **Result files**: Saved in `midscene_run/test-results/<runId>/` by default, including the readable `result.md`, machine-readable `summary.json`, and diagnostic records. Set `--result-dir` to change the results root; relative paths use the command's working directory:
  ```bash
  pnpm exec midscene-test --result-dir ./test-results
  ```
- **HTML report**: Saved in `midscene_run/report/` by default. Open it directly in a browser to inspect case outcomes, screenshots, errors, and replay. Set `output.reportDir` to change the report directory; relative paths use the Test project as their base.

Keep the complete results directory for troubleshooting or programmatic analysis. Use the `summary.json` fields produced by your installed version.

### Artifact directory {#unified-artifact-root-and-migration}

The default artifact directory is `midscene_run/` in the Test project. Reports are in `report/`; results and diagnostic records are in `test-results/`. Set the `MIDSCENE_RUN_DIR` environment variable to change the artifact directory. Relative paths use the Test project as their base:

```bash
MIDSCENE_RUN_DIR="./artifacts" pnpm exec midscene-test
```

In CI:

- Update collection rules from `.midscene/test-results` to `midscene_run/test-results`, or your configured results directory.
- With the [Midscene GitHub Action](https://github.com/web-infra-dev/midscene-action), set `run-directory` or `MIDSCENE_RUN_DIR`. Execution and artifact collection use the same directory.
- Collect files using the printed `Summary:` / `Report:` paths or the SDK's `summaryPath`, `markdownPath`, and `reportPath`. See below for sharing reports.

### Exit codes

You can determine the overall outcome of a test run from the CLI exit code:

- `0`: All selected cases and lifecycle hooks executed successfully.
- `1`: An error occurred during execution (including case step failures, YAML parsing or collection errors, and project-level or file-level lifecycle errors). Even if all case steps pass, the exit code is still `1` if an exception occurs during the cleanup phase.

## Report archiving and URL deep links

### Report archiving

Reports default to a single HTML file: `midscene_run/report/midscene-e2e-<runId>.html`. To choose the delivery format, set `output.reportFormat` in `midscene.config.ts`:

```ts
output: {
  reportFormat: 'single-html', // default: open the HTML directly, including offline
  // reportFormat: 'html-and-external-assets',
}
```

When using `html-and-external-assets`, preserve the entire report directory when archiving or uploading, and view it over HTTP. See [Run in GitHub Actions](#run-in-github-actions) for CI artifact configuration.

### Link to a specific step (URL hash)

When sharing reports in CI notifications, chat bots, or PR comments, use the `runner-step` URL hash parameter to jump directly to a target Step. Beyond explicit Step IDs, reports support portable selectors:

| Selector | Target |
| --- | --- |
| `first` | Earliest started Step |
| `last` | Most recently completed Step |
| `first-error` | Earliest started failed Step, including failed retry attempts |
| `last-error` | Most recently completed failed Step, including failed retry attempts |

Example: Jump directly to the last failed Step in a report:

```text
https://example.com/report/index.html#runner-step=last-error
```

If the Step includes Agent visual replay, append `runner-trace=page` to open the Agent trace in full-screen view:

```text
https://example.com/report/index.html#runner-step=last-error&runner-trace=page
```

To limit selection to a specific case, combine with `runner-page=case`, `runner-project=<projectId>`, and `runner-case=<caseKey>`. Use the report's internal `projectId` and the composite Case Key `<projectId>:<documentId>:<caseId>`. URL-encode each parameter value, for example with `URLSearchParams`. To obtain these values, open the target case in the report and copy its URL, then add `runner-step` and, if needed, `runner-trace`.

## Environment loading {#environment-loading}

Midscene Test reads model configurations and runtime parameters from system environment variables (`process.env`). You can provide environment variables based on your workflow:

### Local development with .env files

- **Scaffolded projects (ready out of the box)**: Projects created via `midscene-test create` already load the `.env` file from the configuration directory in `midscene.config.ts`. Simply create a `.env` file in the project root to get started.
- **Handwritten configuration**: When writing a configuration file manually, import `dotenv` at the top of `midscene.config.ts`:
  ```ts
  import 'dotenv/config';
  ```

When loaded through `dotenv`, existing environment variables in your shell take precedence over values in the `.env` file by default.

### CI / CD environments

In continuous integration (such as GitHub Actions) or automated pipelines, you do not need a `.env` file. Simply inject API keys or credentials directly as pipeline environment variables.

### Model connectivity check (model verify)

When running `midscene-test model verify` to test model connectivity, the command automatically reads `.env` from the current working directory. To facilitate quick local checks, it prioritizes values in `.env` over matching shell environment variables. When troubleshooting, ensure the settings in `.env` match the model configuration used during test runs.

## Run in GitHub Actions

Midscene provides [midscene-action](https://github.com/marketplace/actions/midscene-action) to run Midscene Test in GitHub Actions.

- Automatically add test results to the workflow **Summary**.
- Save HTML reports and test data as **artifacts** for download.
- Optionally publish reports to **Cloudflare Workers** for online previews.

For setup instructions, configuration parameters, and complete examples, see [midscene-action on GitHub Marketplace](https://github.com/marketplace/actions/midscene-action).
