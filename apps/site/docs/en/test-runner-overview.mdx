# Test Runner overview: natural language and extensible Nodes

:::info Project status (Beta)
This document introduces Midscene's new next-generation, general-purpose Test Runner. It separates declarative test cases from programmable extensions and is intended to replace the previous YAML automation solution.

The Test Runner is currently in **Beta**, and its test protocol and APIs continue to evolve. If you have questions or suggestions, we welcome your feedback on GitHub.

(If you are still using the previous solution, see [YAML script runner](./yaml-script-runner).)
:::

## Testing Engineering Challenges in the AI Era

We are living in an era of AI transformation. In moving toward natural language testing, engineering teams face very real transition pain points:

1. **Concerns about the Selector Pattern**: The traditional selector pattern is not only fragile and hard for non-technical staff to maintain, but more importantly, it is based on the DOM tree. It cannot truly simulate what real users see on the screen (such as overlapping elements or broken layouts), failing to maximize the true value of AI's visual and semantic understanding.
2. **The Efficiency Trap of "AI for AI's Sake"**: In the rush to adopt AI, there is often an anxious feeling that "not using AI is outdated." This drives teams to blindly chase 100% AI coverage, forcing simple background tasks (like database seeding or API calls) that could be solved instantly and stably with traditional scripts to be driven by AI. This degrades overall efficiency, inflates costs, and compromises stability—**once trapped, we actually lose our most fundamental pursuits of testing: being faster, cheaper, and more stable.** Introducing AI must be rational: applying the right solution to the right problem.
3. **Organizational Challenges in Combining Engineering and AI**: We believe the future of testing projects must be a combination of "engineering (code) and AI (natural language)." However, existing frameworks often deliver a suboptimal developer experience when trying to organize both. Without clear boundaries and collaboration models, code and natural language can easily become tangled, leading to poor maintainability over time. We need a better organizational form that allows code and natural language to play to their strengths and collaborate seamlessly.

Everyone wants to move toward natural language, but they lack a practical path that connects "deterministic code" with "natural language intent."

## A Hybrid Architecture: Declarative Semantics and Deterministic Engineering

To break this dilemma, `@midscene/test` returns to the first principles of end-to-end (E2E) testing and advocates a **hybrid architecture that balances "Declarative Semantics" and "Deterministic Engineering"**. It divides the test framework into two complementary, equal capabilities that align with two core perspectives in testing teams:

1. **Deterministic Engineering: TypeScript Programming for a Solid Foundation (TypeScript Nodes)**
   **Focuses on "How to support"**. Provides programmable extension capabilities, ensuring the stability, determinism, and high efficiency of the underlying engineering foundation.
   This capability is designed for engineering and platform builders. They use TypeScript to integrate browsers, Agents, external tools, and business APIs, while centrally managing runtime resources and execution lifecycles. Engineering builders only need to declare Zod validation rules and descriptions in their TypeScript Nodes. By encapsulating these technical and business capabilities as reusable custom Nodes, they automatically generate a reference document, eliminating the need to write and maintain API references manually.

2. **Declarative Semantics: Expressing Business Intent in Natural Language (YAML + AI Actions)**
   **Focuses on "What to test"**. Expresses business test intent. Test cases are assembled declaratively in YAML.
   At this layer, authors can describe UI actions (such as `aiAct`) and assertions (such as `aiAssert`) in natural language, while **seamlessly calling and composing custom business capabilities provided and exposed by "Deterministic Engineering" (such as `order.prepare`)** to assemble their own end-to-end business flows.
   This capability is designed for business-centric scenarios. Test authors can write and maintain test cases directly in natural language and declarative nodes, focusing entirely on business flows without needing to write JavaScript or deal with underlying engineering and system details. This significantly enhances authoring efficiency and long-term maintainability.

**Customizing Your Domain-Specific Test Framework and Supporting Capabilities**

The core engineering value of this design is that it empowers developers to **customize and build their own domain-specific test frameworks**. By registering custom Nodes in "Deterministic Engineering" that match your unique business context, you can easily assemble and extend a tailored, highly cohesive testing framework that perfectly fits your team's background and needs.

To help developers build and run these proprietary frameworks with minimal effort and maximum efficiency, we provide a suite of essential supporting engineering capabilities:
- **Unified Observability**: Both AI visual steps and your custom Node executions are centrally recorded in the same execution lifecycle. The test report and runtime logs visualize the inputs, outputs, duration, execution status, and screenshots of every step. This simplifies troubleshooting and replay for human engineers and provides highly structured context for AI Agents to autonomously diagnose issues and optimize test cases.
- **Standardized Lifecycle and Concurrency Control**: Out-of-the-box lifecycle hooks (Before/After), concurrent environment isolation, and sandboxing ensure that your proprietary framework and test cases run stably and predictably in CI (Continuous Integration) pipelines.
- **Auto-Generated Node Reference**: The `describe-nodes` tool automatically compiles registered custom Nodes and their validation rules (Zod Schema) into standard Markdown documentation. This eliminates the cost of manually maintaining API manuals for your proprietary framework, allowing human authors and AI Agents to easily consult and consume these custom capabilities.

### Example Scenario: Verify an Order Refund Flow

Suppose an e-commerce team needs to verify the refund flow for paid orders:

1. **Deterministic Engineering (TypeScript Nodes)**: call an order API or script before each case to create test data, and clean up the test order when the case finishes.
2. **Declarative Semantics (AI Natural Language)**: use YAML instructions to have the Agent submit a refund request in the UI and verify the result.

#### 1. Auto-Generated Node Reference Example

In this scenario, the custom Node `order.prepare` defined by engineering builders automatically compiles into the following Markdown reference using the `describe-nodes` tool:

```markdown
## order.prepare

- **Title**: Prepare order data
- **Description**: Pre-create an order with a specified status in the database.
- **Parameter schema (JSON Schema)**:

{
  "type": "object",
  "properties": {
    "status": {
      "type": "string",
      "description": "Order status, such as paid or refunded."
    }
  },
  "required": ["status"]
}
```

#### 2. Writing and Running Test Cases (YAML)

After reading the reference, test authors (or AI Agents) can directly call and compose the Node in the declarative YAML file:

```yaml
# 1. Deterministic Engineering: prepare data and the environment
beforeEach:
  - order.prepare:
      status: paid
  - browser.openRefundPage: {}

# 2. Declarative Semantics: express business test intent
cases:
  - name: A paid order supports a full refund
    steps:
      - aiAct: Click Apply for refund, select Full refund, and submit
      - aiAssert:
          prompt: The page shows that the refund request was submitted and the refund amount equals the full order amount
          message: Failed to submit the full refund request

  - name: A paid order supports a partial refund
    steps:
      - aiAct: Click Apply for refund, enter a refund amount of 10, and submit
      - aiAssert:
          prompt: The page shows that the refund request was submitted and the refund amount is 10
          message: Failed to submit the partial refund request

# 3. Deterministic Engineering: clean up resources
afterEach:
  - order.cleanup: {}
```

Framework maintainers register custom Nodes such as `order.prepare`, `browser.openRefundPage`, and `order.cleanup` to manage data and pages. Midscene Nodes handle UI actions and assertions. Test intent remains separate from technical implementation, so the two can evolve independently.
