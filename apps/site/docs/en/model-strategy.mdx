# Model Strategy

This guide explains Midscene's model selection strategy.

## Pure-vision localization in Midscene

AI-powered UI automation requires task planning and element localization. The industry mainly uses two localization approaches: combining DOM data with annotated screenshots, or using screenshots directly for pure-vision localization. Midscene uses pure vision, with the model analyzing the UI screenshot and locating target elements directly. UI actions and element localization do not depend on DOM data or extra annotations.

This approach has the following characteristics:

- It does not depend on the UI rendering stack.
- It works across browser Canvas, Android, iOS, desktop applications, and other types of interfaces.
- It can validate what users actually see, including colors, highlighted states, and layout.
- It does not require selectors or extra UI annotations.

Pure-vision localization requires strong visual understanding and processes UI screenshots at runtime. On interfaces with complete component trees and accessibility annotations, structure-based approaches may use fewer model resources. Midscene chooses pure vision to provide consistent interaction capabilities across platforms and rendering technologies.

Since version 1.0, Midscene has used only pure vision for UI actions and element localization. Data extraction and page-understanding workloads can still include DOM data when needed. See the [API Reference](./reference/#extraction-location-assertion) for the relevant options.

## Model responsibilities

Midscene always requires a Default model. Planning and Insight models are optional. When they are not configured separately, their workloads automatically fall back to the Default model.

| Model | Primary responsibility |
| --- | --- |
| Default model | Handles element localization (Locate) and workloads not assigned to Planning or Insight |
| Planning model | Handles task planning for `aiAct` and `ai` |
| Insight model | Handles data extraction, assertions, and page understanding for APIs such as `aiQuery`, `aiAsk`, and `aiAssert` |

After you configure a Planning or Insight model, element localization still uses the Default model. Optional models do not replace the Default model.

## When to use multiple models

For most use cases, a Default model is enough. Consider adding a separate model when different workloads have clearly different capability requirements:

- Configure a Planning model when complex multi-step tasks need stronger planning.
- Configure an Insight model when data extraction, assertions, or page understanding need stronger visual question answering.
- Use different models when you need to balance quality, latency, and cost separately across localization, planning, and page understanding.

A multi-model setup adds model services, environment variables, and call-path complexity. It can also increase latency and token usage. Start with a Default model, then add a separate model only after identifying a planning or page-understanding need.

If task quality is unstable, use [Model debugging and observability](./model-debugging-observability) to identify the problem first. For setup instructions, see [Optional: configure multiple models](./model-common-config#multi-model-combination-example).
