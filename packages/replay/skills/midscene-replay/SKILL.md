# Midscene Replay

**Goal:** deliver one readable `replay/` folder: `index.mjs` declares the flow, `steps/*.mjs` hold one business step each. A business owner replays it with only that folder: `await replay.run(existingAgent)` in their own host, or `node <CLI> run replay/`. Steps are the unit of replay, retry, resume, testing and review. Recordings, trials and `acceptance.md` are authoring evidence; nobody needs to maintain them.

The CLI is `../../scripts/cli.mjs` relative to this skill. Commands load `.env` from the calling directory or `--env-file FILE`. References: [runtime API](references/runtime-api.md), [fallback](references/fallback.md), [session](references/session.md), [commands and review](references/review.md). Templates: [replay folder](templates/replay/index.mjs), [session](templates/session.mjs), [acceptance](templates/acceptance.md).

## Hard rules

1. Requirements come from the user and the original recording, never from what the replay happens to do. Never weaken them after seeing results.
2. Keep the original recording immutable; generated work stays outside it, temporary diagnostics in `scratch/`.
3. One numbered row of the acceptance table is one `defineStep`, in the same order and with the same title. Split at a verifiable business outcome or an independent recovery boundary. Keep supporting actions with that outcome, such as clicking the logo solely to reach the page needed for the next action. Prove each outcome in `done` or in `run`.
4. Bind every target to business identity (destination URL, test ID, scoped text). Treat recording fingerprints as hints. Verify the actual DOM attribute, text or role before using it in a guard. Never use a result rank or `[1]` to hide ambiguity.
5. Business outcomes are program checks. Use Jev only for genuinely visual judgments. Never manufacture results through DOM/application writes or replace required UI steps with direct navigation.
6. A dispatched action is never silently repeated: choose each step's `retry` from its side effects (`idempotent` only when repeating is harmless).
7. Acceptance needs three consecutive complete runs of the same replay, session and requirements with zero fallbacks. After any change, rerun a full group; focused step runs are diagnostics.
8. Inspect actual images and state for every step of every run. Execution success is not business acceptance; missing evidence stays unverified.
9. Keep failed trials and evidence.
10. Run autonomously without pausing for routine confirmation. Only interrupt the flow when genuinely blocked (such as manual login/CAPTCHA, external-write authorization, material business ambiguity, or missing environment/credentials). Whenever you interrupt, clearly state three things in the user's language: what you need, what the user should do next, and what you will do once they respond.
11. Before writing externally, show the environment, account, target, steps and maximum planned writes, and record explicit authorization in `acceptance.md`. For a user-confirmed isolated test environment, ask once for the full acceptance batch plus a bounded number of diagnostic writes and resets. Verify the reset scope. A loopback URL or reset endpoint alone establishes neither isolation nor authorization. Reuse authorization within its scope. A plan marked **shown** does not authorize writes.
12. Before the first recording, replay, trial or visual diagnostic in a task, post a standalone, bold **Recording data risk** notice in the user's language. Say that recordings and reports may save unmasked screenshots, sampled form values, visible content and URLs, including credentials or private data. Name the site and output locations when known. If AI or Jev is planned, mention that screenshots may be sent to the configured model service. Continue promptly after showing the notice. Reuse it for subsequent runs in the same task with the same site, output scope and data handling. Post a follow-up before changing that scope, including newly enabled model transfer or a change of recipient. External-write authorization is separate.

## Workflow

Default end-to-end rhythm: **user invokes skill → Agent starts recording and waits → user says done → Agent automatically prepares and posts the outline table (non-blocking) → Agent authors `replay/` → Agent trials and iterates on the script → Agent delivers final result.**

1. **Record.** Show the notice required by Hard Rule 12, then start `node <CLI> record web --url <START_URL> --out <NEW_RECORDING_DIR>` in a new Chrome window. Ask the user to complete the flow, including popups, then reply when finished or press Enter in the recording terminal. Tell them you will prepare the replay, read this Skill's applicable references and the new recording artifacts, show the outline, then author and verify the replay. Respect any narrower read boundary the user explicitly sets. For recurring signed-in work, use the [dedicated browser setup](references/session.md): open the Replay window once, let the user sign in, then use its local `--cdp` endpoint for `record`, `run`, and `trial`. If the user specifically asks to use their daily browser, follow the same reference for direct attachment. For a different new browser, pass `--browser msedge` or `--browser chromium`. If you cannot expose the browser, give the command and finish instructions.
2. **Prepare (automatic after recording ends).** As soon as the user signals that recording is finished, immediately stop recording and run `node <CLI> prepare <RECORDING_DIR> --out <NEW_WORKSPACE> [--goal TEXT]` without waiting for another prompt. Read `brief.md` (an index with recorded locators), `events.jsonl` and the actual screenshots.
3. **Show outline table (non-blocking by default).** Before scripting, display a numbered business-flow and acceptance table in chat and save it in the prefilled `acceptance.md`: steps numbered from 1 with a kebab-case step id, object identity, entry state, expected outcome and checks, plus goal, initial state and known gaps. Explicitly tell the user in chat in their language that they can interrupt if changes are needed (e.g. "如果需要修改请打断我，默认我将直接继续编写并验证回放脚本。"), mark the table **shown**, and continue immediately without blocking. Mark **confirmed** only on explicit user confirmation or correction. Wait only if the user explicitly asked to approve first. Preserve meaningful input/Enter, revealing hover, filters and same-window/new-window behavior; focus, pointer phases and redirects are evidence, not required units. Omit pure browsing by default. Keep scrolls that reveal a later target, establish a meaningful state, or are explicitly part of the user's goal.
4. **Write the steps.** Copy the template folder to `WORKSPACE/replay/`. Per step: `ready` (entry state; needed to start or resume there), `run`, `done` (exit state), `retry`, and `optional` only for genuinely optional UI such as a banner. Verify the business state in `ready`/`done` and let actions resolve their own locators, so an XPath change does not block an intended recovery. Use `rp.select` for a recorded native single-choice dropdown and verify its business effect in `done`. Use `rp.read` for temporary DOM reads and checkpoints for evidence. Pass step data through `ctx.results` or `ctx.state`, parameters through `ctx.params`. State is shared across attempts. Check required results if an upstream step can recover. Comments and titles in the user's language. Add `guard`/`fallback` where the page is likely to change (see [fallback](references/fallback.md)). Use explicit `rp.scrollIntoView` when a known target needs to be revealed. Give business-critical waits a `title` and prefer feedback tied to the action just performed. Use `session.mjs` when built-in setup cannot establish the start state, including [cross-origin authentication and backend reset](references/session.md#custom-session).
5. **Trial and iterate.** After any necessary read-only diagnosis or write authorization, run `node <CLI> trial replay/` (writes `trials/NN`, three runs, headless; `--headed` to watch). For planned Jev checks on a flow with side effects, [validate the criteria against existing evidence or an isolated fixture first](references/runtime-api.md#diagnose-visual-checks). For signed-in apps, [choose and report the session mode](references/session.md#replay-behavior-with-cdp). On failure, read the failed step's attempts, `steps.md` and `heal.json`, refine the script, and rerun a full group. Use the per-attempt `ready`, `run`, and `done` timings before changing a wait. Use `trial replay/ --step <id>` to replay the prefix through the failing step, or use a [prepared step session](references/review.md#run) to run just that step. Validate dynamic locator variants separately as described in [fallback](references/fallback.md#policy). Pause only on a genuine blocker (follow Hard Rule 10).
6. **Review.** Start with `trials/NN/steps.md` for the frozen inputs, run reports and step images. Open `run-N/review.png` and the original images as needed. Compare with the recording and requirements. Append per-step, per-run pass/fail/unverified to `acceptance.md`, keeping program execution and Agent review separate; mention any retry or recovered step.
7. **Deliver.** Link each run's Midscene Agent Test Report from `steps.md`. Report browser and business-state isolation, checks, model requests, timings and any gaps. Daily use runs the flow once with per-step retries and fallbacks reported. A failed step identifies where to investigate or start a [host-prepared diagnostic run](references/review.md#run).
